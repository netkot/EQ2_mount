# EQ2 Mount Controller — ESP8266 (OneStep_Full_ESP8266_v6)

EQ2 монтировка на ESP8266 с Web UI, RTS2 JSON API и LX200/OnStep TCP (порт 4030).
Подробности протоколов и последних изменений — в шапке `OneStep_Full_ESP8266_v6.ino`.

## Обзор кода прошивки (`OneStep_Full_ESP8266_v6.ino`, ~2200 строк, один файл)

### Архитектура

Один `.ino`, без отдельных модулей/классов. Условно делится на:

1. **Пины и константы механики** (микрошаг, передаточные числа RA/DEC, сидерическая скорость).
2. **`AccelStepper`** — по одному объекту на ось (RA/DEC), режим `DRIVER` (STEP/DIR).
3. **Встроенный Web UI** — вся HTML/CSS/JS-страница лежит одной `R"rawliteral(...)"` строкой
   в прошивке (~380 строк, тёмная тема, разворачивающиеся карточки, статус опрашивается
   через `/status` раз в 2 сек).
4. **`ESP8266WebServer`** на порту 80 — REST-подобные GET-эндпоинты для UI + отдельно
   RTS2 JSON API под `/api/...`.
5. **`WiFiServer` на порту 4030** — свой мини-парсер протокола LX200/OnStep поверх TCP
   (без сторонней библиотеки), с большим `if/else`-диспетчером команд `lxProcessCommand()`.
6. **`ElegantOTA`** — прошивка по HTTP (`/update`).
7. **`TMCStepper`** — настройка драйверов TMC2209 по однопроводной UART-шине на D4
   (микрошаг, ток, StealthChop), контроль связи и сброса драйверов, диагностика `/tmc`.

### Логика движения (`loop()`)

Всё крутится в одном `loop()` без RTOS/таймеров прерываний:
`server.handleClient()` → `ElegantOTA.loop()` → контроль TMC2209 (раз в 5 с, только
когда оси стоят) → RA → DEC → доводка GoTo → пересчёт текущих координат → обработка LX200 TCP.

Каждая ось в каждый момент в одном из режимов: **слю** (`raSlew`/`decSlew`: `moveTo()+run()`
с разгоном/торможением) или **постоянная скорость** (`setSpeed()+runSpeed()`: для RA —
сидерическая + джог, для DEC — джог). Смешивать нельзя: `run()` тянет ось к старой цели
`moveTo()`, и трекинг/джог с ним «дерутся» (так было до v6.1 — трекинг фактически не вёл).
Драйвер RA отключается через `MOTOR_OFF_DELAY` (1 с простоя), кроме активного трекинга.

Особенность: **DEC мотор не отключается после остановки**, если включён `decHoldEnabled`
(по умолчанию `true`) — держит ось, чтобы не проседала под весом (см. предупреждение в UI
про нагрев драйвера без радиатора; в покое TMC2209 сам снижает ток вдвое). RA всегда отключается через 1 сек простоя, кроме
активного трекинга.

### RTS2 JSON API (`/api/*`)

Реализован по мотивам `TelescopeClientJsonRts2.cpp` из Stellarium: `/api/devbytype`,
`/api/deviceinfo`, `/api/get` (координаты/геопозиция/дистанция до цели),
`/api/cmd?c=move+RA+DEC` (GoTo). TLE-команды (`move_tle`) только квитируются —
ESP8266 не считает орбиты спутников.

### LX200/OnStep TCP (порт 4030)

Наиболее объёмная часть файла (~500 строк). Собственный побайтовый парсер кадров
`:CMD#` (с корректной обработкой `:` внутри аргументов вида `:Sr22:01:48#`) и диспетчер,
покрывающий большой набор команд из `lx200driver.h` (INDI) и `OnStepListCmd.txt`:
координаты/цель, GoTo/Sync, halt, tracking rate, park/home, ручной jog, скорости,
импульсное гидирование, статусные биты, время/дата, лимиты высоты, датчики
(температура/давление — статические заглушки), PEC/Library/Rotator/фокусёр — везде
**заглушки-квитанции**, т.к. эта прошивка их не реализует физически (нет PEC, каталога
объектов, ротатора, фокусёра).

Прошивка представляется как OnStep (`:GVP#` → `OnStep#`, `:GVN#` → `10.24b#`), поэтому
с ней работает драйвер INDI **LX200 OnStep** (см. «Подключение к KStars/Ekos»).
LX200 Basic тоже подключается, но умеет только GoTo/Sync/Abort — стрелки ручного
движения в KStars с ним ничего не шлют.

TCP-клиент один: пока подключён INDI-драйвер, новое соединение на 4030 сразу закрывается.

### Особенности и ограничения (важно при доработке)

- **Во флеше (EEPROM-эмуляция) хранится только положение парковки** — механические шаги
  осей, пишутся по Set Park / `:hQ#`. После старта монтировка считается в этом положении
  и запаркованной (поэтому перед выключением её паркуют); если парковка ни разу не
  сохранялась — в доме (противовес вниз, труба на полюс), не запаркована. Дальше `Sync`
  по звезде. При перезагрузке сбрасываются:
  `raMaxSpeed/raAccel/decMaxSpeed/decAccel`, `decHoldEnabled`, геопозиция обсерватории
  (по умолчанию константы `obsLongitude_deg/obsLatitude_deg`, клиент LX200 может задать
  `:St#`/`:Sg#`).
  Позиционирование — чисто программный счётчик шагов, **без концевиков/энкодеров**:
  точность зависит от того, что мотор физически не терял шаги.
- **WiFi SSID/пароль вынесены в `secrets.h`** (не коммитится, см. `.gitignore`).
  В `.ino` — `#include "secrets.h"`. Шаблон для репозитория — `secrets.h.example`
  (плейсхолдеры, коммитится). Перед первой сборкой на новой машине:
  скопировать `secrets.h.example` → `secrets.h` и подставить реальные данные.
- Однопоточная модель — долгие операции в `loop()` (например, `delay()` где-либо)
  просадят одновременно веб-сервер, LX200 TCP и шаг моторов.
- Автоопределение направления AP-режима: если WiFi не подключился за ~20 сек,
  поднимается точка доступа `EQ2-Mount` (пароль `telescope`) как fallback.

## Пины (текущая схема, драйверы TMC2209)

| Функция      | RA (GPIO) | RA (D-label) | DEC (GPIO) | DEC (D-label) |
|--------------|-----------|--------------|------------|----------------|
| STEP         | 4         | D2           | 12         | D6             |
| DIR          | 5         | D1           | 14         | D5             |
| ENABLE       | 0         | D3           | 13         | D7             |
| UART (общий) | 2         | D4           | 2          | D4             |

Активный уровень ENABLE — LOW (см. `enableRA()/enableDEC()`).
Аппаратный Serial (GPIO1/TX, GPIO3/RX) занят под лог на 115200 бод — для UART к драйверам не годится.

Свободные GPIO на плате: **D0 (GPIO16)**, **D8 (GPIO15)**, A0 (только аналоговый вход).
D8 — boot-strap пин, при старте обязан быть LOW: ничего, что тянет его вверх, на него вешать нельзя
(см. «Подключение UART»).

## Физическая сборка — компоненты (по фото)

- **Контроллер** — плата на модуле **ESP-12F** (Wemos D1 mini-совместимый форм-фактор,
  пины 3V3/D6/D5/D8/D7/D0/RST и 5V/D3/D1/D2/D4/G по краям).
- **2× драйвера A4988** — красные платы pololu-формата с чёрными радиаторами, исходная сборка.
- **2× драйвера TMC2209** — чёрные платы того же pololu-формата (шелкография «TMC2209»,
  партия «V985»). **Статус на 2026-10-17:** обе оси перепаяны на TMC2209 и проверены (UART, ток,
  вращение моторов), на VM обоих драйверов стоят конденсаторы. Пошагово — `TMC2209_SOLDERING.md`.
- **Запасной радиатор** (синий, самоклеящийся) — под один из TMC2209, ещё не приклеен.
- **Жгут проводов**: синие — сигнальные (STEP/DIR), красные/чёрные — питание,
  зелёные с белыми JST-разъёмами (парами) — обмотки моторов (подтверждено), идут к
  NEMA17 RA/DEC через разъёмы. Уточнить при монтаже, какая пара на какую ось.
- **Step-down модуль MP1584** (зелёная плата с разъёмом OUT+) — понижает питание для ESP12F,
  см. схему питания ниже.

### Питание

В сборку заведено **одно общее питание 12V**:

```
12V IN ──┬── VMOT драйверов (RA/DEC, A4988 → в дальнейшем TMC2209)   — моторы NEMA17 напрямую на 12V
         └── MP1584 (step-down) → 5V ── 5V-вход платы ESP-12F (бортовой regулятор платы даёт из этого 3.3V)
```

- 12V идёт напрямую на VMOT обоих драйверов — без изменений при переходе на TMC2209
  (у TMC2209 тот же рабочий диапазон VMOT, 12V в норме).
- MP1584 понижает 12V → 5V специально под плату ESP-12F (её вход 5V/логика 3.3V —
  сама плата дальше регулирует 5V→3.3V бортовым LDO).
- При замене драйверов MP1584 и цепь питания ESP не трогаем — она независима от STEP/DIR/EN/UART.

## План перехода на TMC2209

### 1. STEP/DIR/EN — без изменений

Большинство плат-переходников TMC2209 (BTT, FYSETC, Watterott) повторяют разъём A4988/DRV8825
(STEP, DIR, EN, MS1, MS2, VMOT, GND, 2×катушка, VDD/VIO, GND). EN активен по LOW — как и сейчас,
переносим в те же гнёзда без правок кода STEP/DIR/EN.

Проверить перед установкой: логика VIO/VDD модуля должна быть заведена на **3.3V** (от ESP8266),
а не на 5V — иначе пороги STEP/DIR/UART не совпадут с уровнями ESP.

### 2. Микрошаг — через UART, не через MS1/MS2-джамперы

Пока к PDN_UART не идёт трафик, TMC2209 работает в legacy-режиме и MS1/MS2 задают микрошаг
(таблица отличается от 3-пиновой MS1/MS2/MS3 у A4988). Но как только мы поднимаем UART —
драйвер переходит в UART-режим, и MS1/MS2 автоматически становятся пинами **адреса** шины
(см. п.4), а микрошаг (MRES) выставляется программно и должен совпадать с константой
`MICROSTEPS = 16` в коде (`driver.microsteps(16)`).

### 3. Расчёт VREF (ток мотора)

Моторы (по данным с шильдика / datasheet производителя JKONGMOTOR):

| Ось | Модель            | Номинальный ток/фазу | Сопротивление фазы |
|-----|--------------------|-----------------------|---------------------|
| RA  | JK42HS40-1704      | 1.7 A                 | ~1.5–1.65 Ω         |
| DEC | JK42HS60-1206      | 1.2 A                 | ~6 Ω                |

Формула для TMC2209 в legacy/analog-режиме (стандартный модуль, **Rsense = 0.11 Ω** —
свериться по маркировке резистора на плате, встречаются также 0.1/0.15 Ω):

```
I_RMS = [325 mV / (Rsense + 0.02)] × (1/√2) × (VREF / 2.5V)
      ≈ VREF / √2                      (при Rsense = 0.11 Ω)

VREF = I_RMS × √2 = I_RMS × 1.414
```

Диапазон VREF на пине — **0.2–2.2 V**, т.е. через аналоговый VREF максимум ≈1.56 A RMS
физически недостижимо больше. У TMC2209 без радиатора долговременный безопасный RMS-ток
обычно ~1.4 A — гонять RA-мотор на полных 1.7 A постоянно не стоит (перегрев/потеря шагов).

**Рекомендация: старт с ~70% от номинала**, дальше подстраивать по факту (греется/пропускает шаги):

| Ось | 70% от номинала | VREF (fallback, подстроечник) | Через UART (`rms_current()`, мА) |
|-----|------------------|-------------------------------|-----------------------------------|
| RA  | 1.19 A           | ≈1.68 V                        | `rms_current(1190)`               |
| DEC | 0.84 A           | ≈1.19 V                        | `rms_current(840)`                |

Рабочий ток задаётся программно через UART (`rms_current()`, константы `RA_CURRENT_MA` /
`DEC_CURRENT_MA`). Прошивка ставит `I_scale_analog(false)`, поэтому после инициализации UART
подстроечник **не влияет ни на что**. Драйвер округляет ток до своей ступени: для RA
1190 мА → фактически 1160 мА.

Подстроечник — только **аварийный fallback**: им задаётся ток, пока UART не поднят или после
сброса драйвера (до того, как прошивка его перенастроит). Поэтому его всё равно стоит
выставить в район значений из таблицы. VREF меряется между GND драйвера и средним выводом
подстроечника при включённой логике; мотор при этом отключён, 12V снято.

### 4. Подключение UART

PDN_UART — однопроводная шина. Оба драйвера висят на одном узле, ESP работает с ним
**одним пином D4 (GPIO2)** через резистор 1 kΩ, адресация — статическим подтягиванием MS1/MS2:

```
ESP8266 D4 (GPIO2) ──[1kΩ]──┬── PDN_UART (RA,  addr 0: MS1=GND, MS2=GND)
                            └── PDN_UART (DEC, addr 1: MS1=3V3, MS2=GND)
D8 (GPIO15) — НЕ подключать
```

- Используем **SoftwareSerial** в onewire-режиме (RX и TX на одном пине) — аппаратный UART
  занят логом на USB.
- Резистор 1 kΩ ограничивает ток, если ESP и драйвер одновременно тянут линию; приёму не мешает.
- **Почему не D8.** Первая версия схемы вешала RX на D8 прямо на узел PDN. Узел подтянут
  вверх, D8 (GPIO15) при старте оказывался в HIGH, и ESP8266 вообще не загружался:
  в логе на 74880 бод `boot mode:(7,0)` + `waiting for host`, esptool не подключается.
  Правильный старт — `boot mode:(3,x)`.
- GPIO2 (D4), наоборот, при старте должен быть HIGH — подтяжка узла ему помогает. Синий LED
  на GPIO2 мигает при обмене с драйверами — это нормально.
- D0 (GPIO16) не годится для RX SoftwareSerial (нет прерываний) — оставлен про запас.

### 5. Что сделано в коде

- Библиотека `TMCStepper` (teemuatlut, 0.7.3) + `SoftwareSerial` из ядра esp8266 (EspSoftwareSerial 8.x).
- `tmcSerial` в onewire-режиме на GPIO2, 57600 бод (≤74880 — асинхронный RX-ISR, устойчивее при WiFi).
  Обёртка `OneWireUart` включает передачу только на время записи байта — RX в это время
  выключен, собственного эха в буфере нет.
- Два `TMC2209Stepper` (адреса 0 и 1, Rsense = 0.11) на одной шине.
- `tmcInit()` в `setup()`: `pdn_disable`, `mstep_reg_select`, `I_scale_analog(false)`, `toff(4)`,
  `microsteps(16)`, `intpol`, `rms_current(1190 / 840)`, StealthChop с `pwm_autoscale`.
  Результат — в лог USB: `TMC RA: OK, версия 0x21, микрошаг 1/16, ток 1160 мА, IFCNT …`.
  Неотвечающий драйвер — `нет ответа (код 2)`.
- `tmcCheck()` раз в 5 с, пока оси стоят: подхватывает драйвер, который ответил позже
  (12V подали после ESP, распаяли второй), и перенастраивает драйвер после сброса (флаг `GSTAT.reset`).
  Во время движения шина не опрашивается.
- STEP/DIR/EN и `AccelStepper` — без изменений.

### 6. Диагностика по сети

- `/status` — добавлены поля `ra_drv` / `dec_drv` (драйвер настроен и на связи), `fw`
  (дата/время сборки — проверить, что после OTA работает новая прошивка), `up` (аптайм, с),
  `rssi`, `heap` / `heap_max`. Всё это видно и в Web UI, в карточке прошивки.
- `/tmc` — регистры драйверов в JSON: `enabled`, `microsteps`, `rms_ma`, `cs_actual`,
  `stealth`, `standstill`, `ola/olb` (обрыв обмотки), `s2ga/s2gb` (КЗ), `otpw/ot/t120`
  (температура), `sg_result`, `ifcnt`.
- `/tmc-scan` — поиск неисправности шины: уровень линии D4 в покое (`line_idle`: 0 — узел PDN
  закорочен на GND) и ответ по каждому адресу 0–3 (`conn`: 0 — ответил, 2 — нет ответа).
- ⚠️ `/tmc` и `/tmc-scan` читают регистры по UART, и на это время `loop()` стоит —
  десятки мс, при ошибках чтения дольше. **Если опрашивать их во время движения, мотор идёт
  рывками** («поворот — стоп — поворот»), особенно RA (640 шаг/с на 0.1°/с). Читать до и
  после движения; сама прошивка во время движения шину не трогает.
- Прошивка без USB: ElegantOTA, `/update` в браузере или `GET /ota/start?mode=fr&hash=<md5>` +
  `POST /ota/upload` (multipart).

Признаки неисправностей в `/tmc` и `/tmc-scan`:

- `microsteps` стал 8 (RA) / 32 (DEC) и `ifcnt` = 0 — драйвер сбросился и работает в
  legacy-режиме по MS1/MS2 и подстроечнику. Причина — просадка питания VMOT; нужен
  электролит **100 мкФ / ≥25 В** прямо у VM/GND драйвера. После остановки прошивка
  перенастроит драйвер сама.
- `ola/olb` в StealthChop **ненадёжны** — «чистые» флаги не доказывают, что обмотки
  подключены правильно, а на стоящем моторе на удержании `olb` может мелькать ложно.
- **Конфликт адресов:** по адресу 1 никто не отвечает, а ответы по адресу 0 то проходят,
  то нет (оба драйвера отвечают одновременно, при различающихся данных ответы портятся).
  Подтверждение: включить EN у DEC (`/dec-hold?enable=1`) — версия по адресу 0 читается
  как 0 вместо 33. Причина — MS1 у DEC не на 3.3V. Попутно DEC получает настройки RA,
  включая ток 1160 мА — мотор DEC не включать, пока не исправлено.
- **Ошибки чтения RA, пока его мотор под током** (даже стоящий). Похоже на наводки от
  проводов мотора на провод UART; на работу не влияют, т.к. прошивка опрашивает
  драйверы только на стоящих осях. Лечение — развести провод D4–PDN подальше от
  проводов моторов и/или понизить `TMC_BAUD` до 19200.

### 7. Проверка на железе (2026-10-17)

**RA:**


- UART: драйвер отвечает, версия 0x21, микрошаг 1/16, ток 1160 мА.
- Первый jog — драйвер сбросился при включении мотора (см. п.6), повторный — без сбросов.
- Мотор **дёргался на месте** — пары обмоток были перепутаны на стороне драйвера (провода
  от разъёма к драйверу все синие). Лечится перестановкой двух средних проводов; проверка —
  ≈1.5–1.65 Ом между выводами одной пары **на самом драйвере**, обрыв между парами.
- После этого: вращается ровно и тихо. При положительном jog сначала было по часовой,
  после пайки DEC — против часовой (возможно, смотрели с другой стороны, или внутри пары
  поменялись провода — на работу не влияет). `RA_DIR` проверить на монтировке: при
  положительном RA телескоп должен идти с востока на запад.

**DEC:**

- Сначала по адресу 1 не отвечал никто — конфликт адресов (п.6), MS1 у DEC был на GND.
  После перепайки MS1 на 3.3V: адрес 1, версия 0x21, микрошаг 1/16, ток 826 мА (ступень к 840).
- С конденсаторами 100 мкФ на VM сбросов драйверов больше не было, в том числе при
  движении одной оси, пока другая под током.
- Вращается тихо, при положительном jog — по часовой. `DEC_DIR` проверить на монтировке.

**Направления осей на монтировке (2026-10-18):** обе верны, `RA_DIR = 1`, `DEC_DIR = 1`.

- Исходное положение: противовес вниз, труба на Полярную, Sync RA 37.954 / DEC 89.264 (J2000).
- RA+ — против часовой, если смотреть вдоль полярной оси на север, т.е. по вращению неба.
- GoTo DEC 60 уводит трубу от Полярной, DEC+ возвращает к ней.
- Из дома DEC− опускает трубу **на восток** → `HOME_HA_DEG = -90` (см. «Модель координат»).

## Модель координат (v6.1)

- **Время** — NTP (`pool.ntp.org`) сразу после подключения к WiFi. Без NTP (режим AP)
  Web UI сам отправляет время браузера (`/set-time?ms=`), LX200-клиент — через `:SG#` `:SL#` `:SC#`.
  Пока время не задано, GoTo и Sync отклоняются (`time_ok` в `/status`).
- **LST** = GMST (IAU, без нутации) + `obsLongitude_deg`. Проверено: совпадает с ПК до 0.1 с.
- **Механика ↔ небо.** Счётчик RA — механический часовой угол `h` (растёт на запад, как при
  трекинге), DEC — механический угол `d` (90 = полюс). Обычная сторона (`d ≤ 90`):
  HA = h, DEC = d; за полюсом (`d > 90`): HA = h + 180, DEC = 180 − d. RA = LST − HA,
  поэтому при трекинге RA стоит на месте.
- **Дом**: противовес вниз, труба на полюс = `h = HOME_HA_DEG`, `d = 90`. `HOME_HA_DEG = −90`,
  т.к. из дома DEC− опускает трубу на восток (на запад было бы +90). Polar Set (`/set-home`),
  `:hF#` (принять текущее за дом) и `:hC#` (увести в дом) работают с этим положением.
- **Парковка** — отдельное положение, по умолчанию = дом. **Set Park** (`/set-park`, `:hQ#`)
  запоминает текущее положение осей во флеш. **Park** (`/park`, `:hP#`) выключает трекинг,
  ведёт оси туда и ставит «запаркована», только когда оси дошли; пока идут — `:GU#`
  содержит `I` (парковка идёт). Остановка/джог/GoTo во время парковки её отменяют.
  Запаркованная монтировка не принимает GoTo по LX200 до Unpark (`:hR#`).
- **GoTo** выбирает сторону опоры, где противовес ниже оси RA (|h − HOME| ≤ 90°): восточные
  цели — обычная сторона, западные — через полюс. Цели ниже `GOTO_MIN_ALT` (0°) не принимаются.
  После слю — до трёх коротких доводок по RA (за время слю небо смещается).
- **Sync** выбирает сторону опоры, ближайшую к текущему положению осей.
- **Джог**: RA ► — на запад, ◄ — на восток. DEC — механический, независимо от положения
  трубы: + всегда в одну сторону оси, − в другую, по кругу через полюс (механический DEC
  держится в (−90°, 270°]). `:Me#`/`:Mw#` исправлены: раньше были перепутаны.
- **Гидирование** (в отличие от джога) по DEC идёт по небу: север/юг за полюсом
  инвертируются, как ожидают PHD2/Ekos после переворота через меридиан.
- **Эпоха**: RA/DEC — на дату (JNow). Stellarium по RTS2 шлёт J2000 — разница сейчас ~0.35°,
  её снимает Sync по звезде рядом с целью. Прецессии в прошивке нет.
- `DEC_STEPS_PER_DEG` теперь дробный (44.444) — раньше округлялся до 44 (−1%).

Порядок работы: включить монтировку (она в парковке) → Unpark (или Polar Set, если стоит
в доме, а парковка другая) → GoTo на яркую звезду → отцентрировать джогом → Sync → GoTo по
объектам с трекингом → в конце Park и выключить.

## Подключение к KStars/Ekos (INDI LX200 OnStep)

Схема: KStars/Ekos (Windows) → INDI-сервер на Raspberry Pi (`192.168.0.100:7624`) →
драйвер **LX200 OnStep** → монтировка по TCP (`192.168.0.109:4030`).

Настройка:

1. На INDI-сервере запустить драйвер **lx200 OnStep** (не lx200basic).
2. В драйвере, вкладка **Connection**: режим **Network**, адрес `192.168.0.109`, порт `4030`.
   Настройки соединения у каждого драйвера свои — при смене Basic → OnStep они не переносятся.
3. В профиле Ekos Mount = LX200 OnStep **и в оптическом тракте (Train) тоже** Mount =
   LX200 OnStep. Если тракт ссылается на старый драйвер (LX200 Basic), драйвер работает,
   а вкладка Mount в Ekos показывает нули.
4. После перезагрузки монтировки (в т.ч. OTA) драйвер сам не переподключается —
   Disconnect/Connect в Ekos.

Что важно для драйвера (учтено в прошивке):

- По сети драйвер ждёт **каждый** ответ до 2 с, а на молчание части запросов
  (`:%BD#`, `:%BR#`, `:GX95#`, `:GX96#`, `:A?#`) прерывает весь цикл опроса — до статуса,
  скоростей и т.д. он тогда не доходит. Поэтому на все запросы драйвера прошивка отвечает
  сразу: фокусёров нет (`:FA#`, `:fA#`, `:FnA#` → `0`), выходов нет (`:GXY0#`), люфт 0,
  авто-переворот выключен, предпочтительная сторона «лучшая» (`B`), выравнивания по звёздам
  нет (`000`), тип монтировки GEM (`:GXEM#` → `E`), PEC не используется.
- `:GU#` — в формате OnStep: `n` (не ведёт), `N` (нет GoTo), `P`/`p` (парковка), `E` (GEM),
  `/` (PEC не используется), индекс скорости `:Rn#`, код ошибки. Символы `I`, `T`, `W`, `S`,
  `s` слать нельзя — драйвер трактует их иначе.
- Скорости `:R0#`..`:R9#` = 0.25×, 0.5×, 1×, 2×, 4×, 8×, 20×, 48×, 120×, 240× сидерической —
  как подписаны в драйвере. `:RG#`/`:RC#`/`:RM#`/`:RF#`/`:RS#` → индексы 2/5/6/7/8.
  После перезагрузки — 1× (индекс 2): на ней движение стрелками почти незаметно.

Проверить ответы без KStars можно, подключившись к 4030 напрямую (сначала остановить
INDI-сервер — клиент один): `:GU#`, `:GR#`, `:GD#`, `:GVP#`…

## Импульсное гидирование

Команды `:MgnNNNN#`, `:MgsNNNN#`, `:MgeNNNN#`, `:MgwNNNN#` (направление, длительность в мс) —
их шлёт INDI при включённом **Use Pulse Cmd**. Ответа нет, по протоколу. Вариант OnStep
`:MGdNNNN#` отвечает `1` (или `0`, если импульс не принят).

- Скорость поправки — **0.5× сидерической** (`GUIDE_RATE_X`), её же возвращает `:GX90#`
  (гидер берёт её для оценки калибровки).
- **RA:** на время импульса к скорости трекинга прибавляется (запад — быстрее неба) или
  вычитается (восток — медленнее) 0.5×. Проверено: 2000 мс дают ±15.2″ (расчёт 15.0″).
- **DEC:** механика 1:5 без червяка — **81″ на шаг**, мельче ось двигаться не может.
  Импульсы копятся в `decGuideAcc` (дробные шаги), целый шаг делается, когда накопилось ≥1.
  Направление — по небу (за полюсом инвертируется).
- GoTo, ручной джог и `:Q#`/`:Qn#`… сбрасывают текущие поправки. Во время GoTo и в парковке
  импульсы не принимаются.
- Без **Use Pulse Cmd** драйвер гидирует через `:RG#` + `:Mn#`/`:Qn#` — тоже работает, но
  переключает скорость стрелок на 1×.

**Практически:** 81″ на шаг DEC — это ~88 пикселей камеры SV105C на BKP130/650
(0.92″/пикс), поэтому гидировать стоит **только по RA** (Ekos Guide — отключить DEC;
PHD2 — Dec Guide Mode = Off), а DEC-дрейф держать хорошей полярной настройкой.
Для гидирования по DEC нужна более мелкая механика (штатный червяк EQ2 или редуктор).
Гидирование нужно для длинных выдержек (дипскай); для планет/Луны (видео, мс-выдержки)
хватает трекинга.

## Возможные улучшения на будущее

### StallGuard (детект стопора мотора через TMC2209)

Не входит в план перехода на TMC2209, отдельная фича на будущее, после того как драйверы
заработают в базовом режиме (STEP/DIR + UART-ток).

**Идея:** TMC2209 умеет оценивать нагрузку на мотор по обратной ЭДС и отдавать это через
регистр `SG_RESULT` (по той же UART-шине, что уже поднята под ток/микрошаг — доп. проводка
не нужна). Т.к. у монтировки нет концевиков/энкодеров (см. «Особенности и ограничения»),
StallGuard может частично закрыть эту дыру:

- **Sensorless homing** — медленный подвод оси до механического упора, детект стопора как
  «домашняя точка» вместо ручного `Sync`.
- **Защита от заклинивания при GoTo** — остановка мотора при упоре/перекосе вместо тихой
  потери шагов.
- **Аварийный стоп при ручном jog** — упор в раму/противовес.

**Нюансы, которые надо учитывать при реализации:**

- Свободны D0 (GPIO16) и D8 (GPIO15, boot-strap — при старте обязан быть LOW) — на два
  DIAG-пина впритык и с риском для загрузки, поэтому читать стопор нужно через регистр `SG_RESULT` по UART, а не аппаратным
  DIAG-пином.
- StallGuard ненадёжен на малой скорости — на сидерическом трекинге показания зашумлены,
  практически применим только на GoTo/быстром слежении (регулируется порогом `TCOOLTHRS`).
- Показания стабильнее в режиме **spreadCycle**, чем в StealthChop (`pwm_autoscale`) — возможна
  схема «StealthChop на трекинге (тихо) / spreadCycle на GoTo (надёжный StallGuard)»,
  переключается `driver.en_spreadCycle(true/false)` на лету.
- Порог `SGTHRS` подбирается эмпирически на реальном железе.
- Опрос `SG_RESULT()` — не каждую итерацию `loop()`, а раз в 50–100 мс во время GoTo, чтобы не
  забивать общую UART-шину.
